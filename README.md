# BT 资源搜索工具包

自己爬、自己建索引、自己搜的 BT 资源检索系统，外加从现成资源库批量导入的能力。

[English README](README.en.md)

纯 Python 标准库，不用装任何第三方包。需要 **Python 自带的 SQLite 在 3.43 以上**（见下面「Python 和 SQLite 版本」，这一条不能按 Python 版本推）。当前构建 **2026-09-14-b**（每个工具启动时会打出来，用来确认版本）。

## 一分钟上手

1. 拿到代码，放在一个**自己可写**的目录里：

   ```
   git clone https://github.com/sailinsky76/btsearch-toolkit.git D:\btsearch
   ```

   不用 git 也行，仓库页面「Code → Download ZIP」解压出来一样。**别放 Program Files**，那里默认不可写。
2. 双击 `check.bat` 自检，全是 OK 再往下走。第一次跑最可能卡在 SQLite 版本上，它会直接告诉你怎么办。
3. 双击 `web-admin.bat`，浏览器自动打开。
4. 点右上角**「任务」**，爬虫和导入都在里面点几下就能跑。

不用记命令行。只有 `web-admin.bat` 那个窗口要一直开着，它是网页服务器本身。

要把搜索页给别人用，另有一个只能搜索的 `web-user.bat`，见「搜索 → 网页 → 管理版和用户版」。

想用命令行也行，后面每一节都有对应的命令。

## 任务面板

> 这一节讲的全是管理版（`web-admin.bat`）的功能。用户版 `web-user.bat` 带 `--no-tasks`，页头上没有「任务」按钮，手敲 `/tasks` 也是 403。

浏览器打开 `http://127.0.0.1:8080/tasks`，或者从首页右上角的「任务」进。三块：

**DHT 爬虫** —— 填端口和线程数，点启动。下面实时滚动显示抓到的种子和统计行，点停止就停。参数含义见后面「DHT 爬虫」一节。

**导入外部资源** —— 选来源（Jackett / 本地种子文件夹 / 互联网档案馆 / Academic Torrents），填对应参数，点开始。选不同来源时表单会自动切换该填的字段。

本地种子那块有个**「浏览…」**按钮，点开能一级级点进文件夹选，不用手敲路径。每进一个目录会顺带告诉你「这个文件夹下有 N 个 `.torrent`」（递归数的），点进去就知道站没站对地方。

> 为什么要服务端来列目录：网页拿不到本地绝对路径。`<input type="file">` 出于安全只交文件名和相对路径，而 `btimport` 要的恰恰是 `D:\torrents` 这种绝对路径。好在服务本来就跑在你自己机器上。这个接口跟任务面板一起开关，加 `--no-tasks` 会连它一并关掉；它只回目录名和计数，不回文件名、不读任何文件内容。

**维护** —— 体检、修复索引一致性、整理磁盘空间、实测做种情况，各一个按钮。

每种任务同时只能跑一个——爬虫开两份会抢端口，导入开两份会互相拖慢。日志区每 2 秒刷新一次，滚到底部时会自动跟随，你手动往上翻看历史时不会被打断。

关掉网页时，它启动的后台任务会一起收掉。

### 安全上的取舍

**让网页能启动进程是个不小的权限扩大**，所以做了这些限制：

- 命令行是按固定模板**组装**的，不是拼接的。接口只收任务种类和具名参数，数字全部取整并夹到合理区间，路径和地址作为独立参数传递，全程不经过 shell
- 和删除接口一样要过随机令牌和同源校验
- 默认只监听 `127.0.0.1`

实测过各种注入尝试（端口里塞分号、参数塞命令替换、伪造任务种类等），都被拦在组装阶段。

**但如果你把 `--host` 改成 `0.0.0.0`，一定要同时加 `--no-tasks --no-delete`**，否则局域网里任何人都能在你机器上启动进程、清空你的库。

```
py -3.11 btweb.py --db bt.db --no-tasks          只关任务面板
py -3.11 btweb.py --db bt.db --no-tasks --no-delete   对外开放时该用的
```

最后这一行不用自己敲，`web-user.bat` 就是它，见「搜索 → 网页 → 管理版和用户版」。

### Python 和 SQLite 版本

所有 `.bat` 都通过 **`py -3.11`** 调用。这一行写在 `_env.bat` 第一行，换版本只改这一处：

```bat
set "PY=py -3.11"
```

找不到 3.11 会自动退到 `py -3`，再退到 `python`，全都没有会提示装 Python 然后退出。

语法上 Python 3.8 及以上都能解析（全部文件按 3.8 规则重新解析过确认）。但**真正的门槛是 Python 自带的 SQLite，要 3.43 以上**：索引用的是无正文 FTS（`content=''` 加 `contentless_delete=1`），那是 3.43 引进的，低于这版连库都建不出来，报一句 `unrecognized option: "contentless_delete"`。

**这个门槛不能按 Python 版本推。** 同一个 3.11，小版本不同带的 SQLite 也不同。自己查一下：

```
py -3.11 -c "import sqlite3; print(sqlite3.sqlite_version)"
```

低于 3.43 就去 python.org 换个新一点的安装包，3.12 及以上肯定够。`check.bat` 会实际按索引真用的那个表结构建一张试，建不起来当场报失败——不是光看版本号，也不是只试一张普通 FTS 表。

直接用 Python 调也行，每个脚本都有 `--help`：

```
py -3.11 btindex.py --db bt.db search 关键词
```

## 先理解一件事

**DHT 网络本身不支持按关键字搜索。** 协议里只有一个操作——「谁有 infohash 为 XXX 的种子？」。你没法问它「有哪些种子名字里带某某」。

所以关键字搜索只能靠先把索引建起来，再搜自己的库。填库有两条路：

| | 速度 | 内容 | 依赖 |
|---|---|---|---|
| **批量导入** | 快，一次几千到几万条 | 现成索引站已整理好的 | 能访问那些站点 |
| **爬 DHT** | 慢，一天几千条 | 当下网络上实际在流通的 | 需要出网能力，入站可达更好 |

**想快就先导入。** 爬虫适合长期挂着慢慢积累，两边存同一个库，搜索时自然合并。

```
   外部资源库                        DHT 网络
   Jackett / 档案馆 / 本地种子           │ 嗅探 announce 和 get_peers
        │                              ▼
   btimport.py ──────► bt.db ◄───── dhtsniff.py + dhtmeta.py
                         │
                         ├──► btweb.py     网页搜索
                         ├──► btsearch.py  命令行 + 实时聚合外部源
                         ├──► btpeers.py   查真实做种人数
                         └──► btprune.py   清死种、修索引
```

## 搜索

### 网页

双击 `web-admin.bat`，打开 `http://127.0.0.1:8080`。支持中英文、按体积筛选、按热度/体积/时间排序，点标题看文件列表，点「复制」拿磁力链。

默认**只监听本机**。要在局域网里用，加 `--host 0.0.0.0`——但这个页面没有任何登录控制，想清楚再开。

#### 管理版和用户版

两个启动脚本，跑的是同一个 `btweb.py`，区别只在启动参数：

| | `web-admin.bat` | `web-user.bat` |
|---|---|---|
| 端口 | 8080 | 8081 |
| 页头「任务」按钮 | 有 | 没有 |
| 列表上「编辑列表」 | 有 | 没有 |
| `/api/task`、`/api/browse` | 通 | 403 |
| `/api/delete` | 通 | 403 |
| 可写连接 | 删除时临时开一条 | 永远不开 |

（读连接两版都是只读的，一直如此，跟这两个开关无关。`--no-delete` 管的只是那条临时可写连接。）

用户版不是把按钮藏起来就算完，接口一并关掉了——只藏按钮的话，知道地址的人直接发请求照样能在你机器上起进程、清你的库。页面上那些「去任务面板点一下」的提示也跟着收起来，用户版进不去面板，留着只是把人指到一堵墙上。

端口特意错开，两个可以同时开着：自己用 8080，把 8081 给别人。索引是 WAL 模式，两个进程同时读、外加爬虫在写，都不会互相锁死。

> 早先版本里的 `web.bat` 已经去掉了，用 `web-admin.bat` 代替。桌面快捷方式、任务栏固定项或者开机启动里如果指着老名字，记得改一下。

#### 开给局域网

改 `web-user.bat` 里的 `HOST=0.0.0.0`。另外两件事得一起做，不然会卡住：

**放行防火墙的 TCP 端口。** `install-firewall.bat` 开的是爬虫要的 **UDP 6881-6888**，不管网页。网页端口没放行的话，你这边浏览器打得开（走的是本机回环），别人却连不上，而且什么报错都没有。管理员身份开 cmd：

```
netsh advfirewall firewall add rule name="BT Search Web" dir=in action=allow protocol=TCP localport=8081
```

**这个页面仍然没有任何登录。** 能连到这台机器的人就能搜你的整个索引。只在信得过的局域网里开，别往公网放；真要放公网，前面自己加一层认证或者反向代理。

顺带一提，对外开放时「空手打开首页会回到上次看的那一屏」这个便利会自动关掉——那份记录是全进程共用的，没有会话概念，多人用的时候它会把上一个人搜过的词直接送到下一个人的地址栏里。只监听本机时照常。

### 浏览全部（不用关键词）

网页上**搜索框留空直接点搜索**，就会按最近出现的顺序列出库里所有条目——当前的筛选照样管用，所以「只看剧集」「只看 2160p」这些搭配着用就是分类浏览。顶上的下拉可以按**来源**筛（dht / torznab / ia / folder，括号里是各自条数），排序和体积筛选一样管用，下面照常翻页。

命令行：

```
py -3.11 btindex.py --db bt.db list                          最近入库的 50 条
py -3.11 btindex.py --db bt.db list --source torznab -n 100  只看某个来源
py -3.11 btindex.py --db bt.db list --sort size -n 20        按体积
py -3.11 btindex.py --db bt.db list -n 50 --offset 200       翻页
py -3.11 btindex.py --db bt.db list -n 99999 --magnet > all.txt   导出全部磁力链
py -3.11 btindex.py --db bt.db list -n 99999 --tsv > all.tsv      导出 TSV
```

`--sort` 可选 `date`（默认，最近出现）、`hits`（热度）、`size`、`name`、`random`。

### 怎么算命中

多个词是 **AND**：`ubuntu server` 要两个词都在。

两个操作符：

| 写法 | 意思 |
|---|---|
| `matrix -reloaded` | 排除。命中 matrix 但不要含 reloaded 的 |
| `黑客帝国 -枪版 -cam` | 排除可以叠几个 |
| `"the matrix"` | 按相邻匹配。不会命中 the 和 matrix 分散在名字两头的条目 |
| `-"web dl"` | 两个能一起用 |

减号只在**词首**算数，所以 `WEB-DL`、`S01-S10`、`ImageNet-ILSVRC2012` 这些名字里的连字符照常是内容，不会被当成操作符。

**排除词和普通词用同一套前缀规则**，也就是说 `-1080` 会把 `1080p` 一起排掉。本来想让排除走精确匹配少误伤一点，但那样 `1080` 搜得到 1080p、`-1080` 却排不掉 1080p，同一个词加不加减号行为不一样——这种不一致比多排掉一点更难受，而且排除是你自己打出来的，不是工具替你做的决定。

**只给排除词（`-枪版`）搜不出东西**，页面会直接告诉你。那等于「全库减去它」，几百万条，翻不动也没意义。

中英混排的短语（`"the matrix 复仇"`）会**退化成 AND**。索引里中文二元组排在前面、拉丁词排在后面，两者根本不相邻，按短语查必然一条都搜不到——与其给个静默的零结果，不如多给点结果。

排除和短语在**命令行、网页、以及「删除当前筛选的全部」上是同一套**，不会出现看到的和删掉的不是一批。

**英文和数字按前缀匹配**，3 个字母以上的词才算数：`ubun` 搜得到 `ubuntu`，`x86` 搜得到 `x86_64`。两个字母以内（`ub`、`21`）还是精确匹配——一两个字母的前缀能对上成千上万个不同的词，那就不是搜索是扫库了。

这条规则真正解决的其实不是「打了半个单词」，而是下面这种：

| 搜什么 | 旧版 | 现在 |
|---|---|---|
| `1080p` | 31 条 | 31 条 |
| `1080` | **0 条** | 31 条 |
| `2160` | **0 条** | 7 条 |
| `ubun` | 0 条 | 2 条 |

字母和数字连在一起在索引里算**一个词**，`1080p` 整个是一个 token，所以旧版搜 `1080` 一条都出不来——库里明明有几十条。同类的还有 `x264`、`S01E05`、`amd64`、`2160p`。

所有英文词都加前缀，不是只加最后一个。只加最后一个的话 `matrix 1080` 搜得到、`1080 matrix` 搜不到，同样两个词换个顺序结果就变，在搜索框里这种不一致比多一点噪音难受。

**中文不受影响。** 索引里的中文 token 全是两个字的二元组，加前缀能多匹配到的两字词就只有它自己，等于没加。单个汉字照旧走 LIKE 回退。

嫌噪音大或者嫌慢，命令行加 `--exact` 关掉前缀：

```
py -3.11 btindex.py --db bt.db search 2160 --exact     只找恰好叫 2160 的
```

网页上没有这个开关——真要关，改 `btindex.py` 里的 `PREFIX_MIN`，调大到比一般词还长就等于全关了。

### 名字命中排在文件列表命中前面

全文索引分**两列**：名字（含中文二元组）和文件列表（含二元组）。搜索时两列都搜，但排序时**名字的权重是文件列表的十倍**。

这一条是拿实测逼出来的。合成一列的时候，搜 `matrix` 出来的前十名全是这种东西：

```
Dev Tools Pack 0          ← 名字里没有 matrix，只是文件列表里有个 bin/matrix.dll
Dev Tools Pack 1
...
```

真正的 `The Matrix 1999 1080p BluRay x264-CHD` 一条都进不了前十。原因不是 bm25 算错了，而是它按文档长度归一化：`Dev Tools Pack 0` 加两个短文件名，整体比电影那串技术后缀短得多，于是得分更高。拆成两列加权之后，同一个查询前六条全是黑客帝国。

中文那边本来就没这个问题（二元组展开让名字这一份足够重），所以这次改动主要修的是英文和混排的名字。

结果行上会标出来是哪一列命中的：名字里不含关键词的条目，行尾挂一个「文件名匹配」。搜索两列一起搜，所以这类条目本来就会出现在结果里，而看页面的人只看得到名字，第一反应是「这条为什么在这」——那个答案原先要点开详情页翻文件列表才知道。判断用的是 `btindex.name_matches()`，跟 `build_match` 同一套分词规则（中文按二元组逐个查，拉丁够长的按前缀，短语按相邻），两边错开就会标反，所以它和查询构造钉在同一组自测里。没有关键词时（浏览全部）不标。

权重取 10 不敏感：实测到 2 就已经翻过来了，2 到 30 之间前十名的构成完全一样。也确认过不会把「合集」类资源埋掉——它们本来就因为文件列表长被长度惩罚压在后面，和权重无关。

**老库要迁一次才有这个效果**，见「从旧版升级」。没迁的库照常能搜，只是排序还是老样子。命令行和网页用的是同一组权重。

### 重复发布会折起来

同一个种子被不同的人重新做一遍（换 tracker 列表、换分片大小），infohash 会变，于是库里就有好几条一模一样的东西。网页上这类条目**折成一条**，行尾标 `+3 条同名`，上方那行说明写清楚本页折了几条，点「展开」就还原。

**判据是名字、体积、文件数三样全等**，不做任何名字解析。infohash 是主键，同一个种子本来就进不来两次，所以库里剩下的重复恰好就是这一类。

**为什么不按解析出来的片名折**（也就是把《黑客帝国》的十几个版本并成一条）：那要先归一化标题，而归一化一定会认错，认错的方向是把两部不同的片并成一条——你看不到被藏起来的那条，也不知道自己少看了什么。假分裂只是跟现在一样，假合并是在骗人，两种错的代价不对称。现在这个键近乎是证明：同名、同一个字节数、同一个文件数还不是同一份东西，实际上碰不到。

**体积必须进键。** 光按名字折不安全——同名不同体积就是不同内容（重压过的、带不带花絮的），并成一条正是上面说的那种假合并。

代表条目取**当前排序下排在最前面的那个**，不是做种人数最多的那个。排序已经按你选的标准挑过一遍，再换个标准挑代表，显示出来的那行就和它所在的位置对不上——按时间排的列表里某一行比上面那行还旧，看着像排序坏了。组里各条内容完全相同，谁当代表都能下到同样的东西。

只在**本页取到的这批行**里折，不跨页。相关度排序下同名同体积的条目 bm25 得分相同、必然相邻，这个限制几乎不起作用；按时间排时偶尔有一组被页边界切开，那一条会在两页上各出现一次。

**折叠状态下删除会删掉整组。** 勾一条只删代表的话，剩下的重复会顶上来，看着像没删掉。所以勾选框带的是整组的 infohash，按钮上的数字也是真要删掉的条数——勾一个框、写着「删除选中 4 条」，删的就是 4 条。

**选中可以跨页攒。** 第一页勾几条、翻到第三页再勾几条，一起删。点进某一条看看再回来，选的东西也还在——那是一次往返，不是重新搜了一轮。

**选中集和编辑状态同生共死。** 换查询词或换筛选条件之后点搜索，页面会回到浏览状态（搜索表单里不带 `edit`），这时选中集一并清空。不清的话它既不显示也点不到，下次进编辑却会凭空冒出来。退出编辑、删除完成、点「清空选择」同样会清。整份存在 sessionStorage 里，关掉标签页也就没了——不用 localStorage 是因为删除不可撤销，一份昨天的选中活到今天再被顺手点掉，是这里最不该发生的事。

跨页选最危险的地方是**选了但看不见**，所以工具条上一直摆着「已选 N 条，其中 M 条不在本页」，点删除时确认框里会再说一遍。一次最多选 2000 条。

折叠行代表好几条，勾一下就是整组进选中集。展开之后那几条各自成行，会各自显示为已勾；取消掉其中一条再折回去，折叠行就不再是勾上的状态——少一条就不算全选，半选状态不撒谎。

**编辑状态也在 URL 里**（`?edit=1`），所以翻页、点进详情再回来都不会掉出编辑。原先它只是 body 上的一个 class，翻一页就没了。

**折叠只影响显示。** 页头的「库里 N 条」、「当前筛选下 N 条」、以及「删除当前筛选的全部 N 条」都是真实条数，不受折叠影响。

### 还有没有人做种

搜索结果每一行右边会写实测的做种情况。**三种状态含义完全不同，别混起来看**：

| 显示 | 意思 |
|---|---|
| `42 人 · 1 小时前` | 测过，当时有 42 个 peer |
| `215 人 · 1 个月前` | 测过有人，但**这个数已经旧了**，颜色会暗一档 |
| `没人做种 · 1 天前` | 测过，当时一个人都没有，多半是死种 |
| `做种 未测` | **从来没测过**，不知道有没有人 |

最后两行是最容易看错的地方：「没人」和「未测」在界面上必须分得开，一个是结论，一个是还没问过。库里的条目默认都是「未测」。

配套的两个入口：排序下拉多了「做种数」，筛选那排多了勾选框**「只看还有人做种的」**（判据是实测 peers > 0，把「未测」算进来就没意义了）。

数据从哪来：任务面板的**「实测做种情况」**按钮，或者命令行 `btpeers.py scan`。它会去 DHT 上一个个真查，慢，所以是批量后台跑的，不是搜的时候现查。刚建的库勾上「只看还有人的」会一条都没有——那不是没资源，是还没测过。

超过 **14 天**的数据就标成旧的。三个月前测出来有 40 个人，今天可能一个都不剩，把陈年数字和刚测的显示成一样是在骗人。

顺带一个反直觉的实测结果：**勾上「只看还有人的」之后，搜高频词反而更快。** 20 万条的库里搜 `1080p` 命中近 5 万条，不加筛选 0.058–0.107 秒，加了 `peers > 0` 是 0.026 秒，稳定快一倍。原因是被筛掉的行根本进不了排序那一步，bm25 也就不用给它们算分。这个筛选既是功能也是性能杠杆，而且正好作用在最慢的那类查询上。

### 分类和清晰度

**下拉里那个条数跟着当前的其他筛选走。** 筛成某个来源之后，分类里列出的就是这个来源下的分布；点了必然是零条的档次直接不列。原先数的是全库——省下了每次重数的开销，代价是那个数字紧挨着筛选项、人会把它读成「点下去能拿到多少条」，而筛完之后它就是错的。

每个下拉**不含自己那一维**：算分类分布时不带分类条件。带上的话，选了「电影」以后别的分类全是零条、被藏光，就再也切不回「剧集」了。

开销上分两条路：一条筛选都没有时走原来那套缓存，这是最常落到的情形，性能没变；带上筛选就实算，封顶五万行加超时守着。**数不出来时下拉照列选项、只是不带数字**——偏的比例比没有数字更坏，而藏掉选项等于替人断定「这里没东西」，可我们恰恰不知道有没有。

筛选那排还有**分类**和**清晰度**两个下拉。它们不是关键词，是从种子名里解析出来、存成列的两个字段：

| 分类 | 怎么判出来的 |
|---|---|
| 电影 | 是影视内容，有年份，没有季集标记 |
| 剧集 | 有 `S01E05`、`第2季`、`第15集`、`全24集`、`Complete Series` 这类标记 |
| 影视 | 是影视内容，但看不出是电影还是剧 |
| 音乐 / 游戏 / 软件 / 图书 | 见下面「靠什么判」 |
| 未识别 | 名字里认不出东西。这一档也能单独筛，用来看规则漏了什么 |

清晰度分四档：`4K/2160p`、`1080p`、`720p`、`480p 以下`。**4K、UHD、2160p、3840x2160 会归到同一档**——这正是它值得单独存一列的理由：这四种写法搜词搜不到一起，列可以。

**为什么只有这两样进库。** 解析器其实还认年份、第几季第几集、片源（BluRay / WEB-DL / Remux / HDTV / DVD / 枪版）、编码（x264 / x265 / AV1 / XviD）和发布组，这些都显示在结果行和详情页上，但**不存进库**。判据是「归一化之后有没有变得更有用」：年份在名字里本来就是一个独立的词，搜 `2019` 和 `year=2019` 命中的是同一批东西，多存一列只是多一份要维护的真相。而「剧集」压根不是一个词——没有哪个 token 的意思是「这是一部剧」，只能推断，所以它必须是列。

**靠什么判。** 文件列表是最硬的证据：里面七成以上是 `.flac` 就是音乐，是 `.epub` 就是图书，名字里怎么写都不改这个结论（跟着来的文件不投票——字幕、封面图、说明文档不算数）。没有文件列表时（Jackett 导入的条目就没有）才看名字里的词。游戏关键词排在文件列表前面，因为游戏包里多半是 exe 和一堆 bin，按扩展名投票会投成「软件」。

**这套规则会认错。** 名字是人随手拼的，没有标准。所以有个命令专门用来挑错：

```
py -3.11 btparse.py sample --db bt.db -n 30        随机抽 30 条，名字和解析结果并排看
py -3.11 btparse.py sample --db bt.db --kind ""    只看认不出来的那些
py -3.11 btparse.py try "Some.Show.S02E07.1080p.WEB-DL.x265-GRP"
py -3.11 btparse.py stats --db bt.db               各分类占比、还有多少条没解析
```

规则改完跑 `py -3.11 btparse.py test`，37 条用例会跑一遍；`check.bat` 里也有这一项。

**老条目要回填一次。** 新进来的条目入库时就解析好了，升级之前就在库里的那些还是空的，筛不出来。任务面板点一次**「解析名字」**，或者：

```
py -3.11 btparse.py backfill --db bt.db
```

不联网，20 万条大约 7 秒，随时能 Ctrl-C，下次接着上次的来。每周维护（`maint.bat`）也会顺手补，所以挂着计划任务的话不用管。

**又一个性能杠杆。** 和「只看还有人做种的」是同一个道理：20 万条的库里搜 `1080p` 命中 14 万条，不筛 0.145 秒，加上「分类=剧集」0.104 秒，加上「分类=音乐」（这个词几乎不出现在音乐名里）0.029 秒。被筛掉的行进不了排序那一步，bm25 不用给它们算分。

## 填库方式一：批量导入

```
py -3.11 btimport.py probe                 探测各个源通不通
py -3.11 btimport.py ia --limit 20000      互联网档案馆
py -3.11 btimport.py academic              科研数据集
py -3.11 btimport.py folder D:\torrents    本地已有的 .torrent
py -3.11 btimport.py torznab "地址|APIKEY" --query 关键词
```

选项写在子命令前面或后面都行。导进来的条目和自己爬的存同一个库，用 `source` 字段区分。

默认值：`--limit 5000`、`--workers 8`、`--delay 1`、`--timeout 30`。并发别调太高，档案馆和 Academic Torrents 都是公益服务器。

### 用 Jackett 接入索引站（推荐，接入面最广）

**API Key 不用注册。** 它是 Jackett 装到你电脑上之后自己随机生成的本地凭证，跟任何在线服务无关。（Jackett 里添加的**私有站点**可能需要那个站点的账号，公开站点不用。）

**步骤：**

1. 去 [Jackett releases](https://github.com/Jackett/Jackett/releases/latest) 下 `Jackett.Binaries.Windows.zip`，解压运行 `JackettTray.exe`
2. 浏览器打开 `http://127.0.0.1:9117`
3. 点 **+ Add indexer**，筛 `public` 类型多加几个站。每个加完点右边的 **Test** 先单独验一下
4. **API Key 在页面顶部**，一长串十六进制，点一下复制
5. 地址用 `all` 表示搜所有已配置的站：

```
http://127.0.0.1:9117/api/v2.0/indexers/all/results/torznab/api
```

6. **先逐个测，看哪些站在你的网络里能用**：

```
py -3.11 btimport.py probe torznab "http://127.0.0.1:9117/api/v2.0/indexers/all/results/torznab/api|你的APIKEY" --each
```

输出会分成四类，每类给对应的命令：

```
  0magnet         20 条，只给种子地址    需 --fetch-torrents        0 秒
  1337x          HTTP 400：IndexerException                      42 秒
  52bt            20 条，20 条有磁力链  直接可用                     4 秒
  anibt          连得上，但没返回条目                                1 秒
```

- **直接可用** — 有磁力链，直接导
- **只给种子地址** — 加 `--fetch-torrents`，把种子下下来自己算 infohash
- **连得上但没返回条目** — 站点是通的，只是探测词没命中。动漫站换番名试试
- **不通** — Jackett 连不上，看下面的排错

7. 正式导入。**用单个能用的站，别用 `all`**——`all` 要等所有站返回，一个慢的就拖垮整批：

```
py -3.11 btimport.py torznab "http://127.0.0.1:9117/api/v2.0/indexers/52bt/results/torznab/api|你的APIKEY" --limit 50000 --pages 30 --delay 2 --timeout 120
```

只给种子地址的站加一个开关：

```
py -3.11 btimport.py torznab "...0magnet..." --limit 50000 --pages 30 --delay 2 --timeout 120 --fetch-torrents
```

**关于扫描范围：** 给了 `--query` 就只导这个词。不给会用内置的 60 个扫描词（空查询 + 数字 + 字母 + 常见中文字），每个词最多翻 `--pages` 页（默认 5，每页 100 条）。想尽量抓全就把 `--pages` 调大。`--terms "电影,电视剧,动漫"` 可以自己指定词。

**`--delay` 别设太小。** 几十个词乘几十页就是上千次真实搜索请求，站点限流甚至封 IP 都可能。默认 1 秒，建议 2-3 秒。中途 Ctrl-C 已导入的会保留。

**建议先小批量确认**：`--limit 200 --pages 3` 跑一次，看 `btindex.py stats` 里 `torznab` 涨了多少，再放开。

Prowlarr 是 Jackett 的后继者，Torznab 地址格式一样，同样能接。

### 互联网档案馆

量最大的公开库，五千万级条目，每个都自动生成种子。

```
py -3.11 btimport.py probe ia
py -3.11 btimport.py ia --limit 20000
py -3.11 btimport.py ia --query "mediatype:movies AND year:[2000 TO 2025]" --limit 50000
```

内容偏公有领域：老电影、老软件、有声资料、各类存档。

#### `--query` 怎么写，决定了你会搜到什么

用的是 Lucene 语法，**不写字段名的裸关键词会搜遍所有元数据**——简介、主题词、上传者、所属合集，书籍还包括扫描全文。而入库时只存 `title` 一个字段：

```python
title = md.get("title") or identifier      # -> name
```

所以直接写「奥德赛」搜出来的结果里，会有一批**名字和文件列表都不含这个词**的条目。它们不是搜错了，是靠简介或主题词命中的，而那部分你库里没存，在页面上当然看不到。

想按名字搜，就写上字段名：

| 想要什么 | `--query` 写什么 |
|---|---|
| 只匹配标题（多数时候要的是这个） | `title:(奥德赛)` |
| 标题 + 按类型收窄 | `title:(odyssey) AND mediatype:movies` |
| 整个合集 | `collection:(prelinger)` |
| 按主题词 | `subject:(jazz) AND mediatype:audio` |
| 排除书籍 | `title:(space) AND NOT mediatype:texts` |

**加 `mediatype` 收窄很值。** 档案馆里 `texts`（书籍）占绝对多数，而且**书的扫描全文是被索引的**——不排掉的话，搜任何常见词都会灌进来一大堆书。这通常是「搜出来的东西看着毫不相干」的主要来源。常见取值：`movies`、`audio`、`texts`、`software`、`image`、`data`。

还有一处会让关键词「消失」：**文件列表最多存 60 条**（`nfiles` 仍是全量计数，所以你会看到「200 个文件」但详情页只列 60 个）。关键词落在第 61 个文件上就存不进来。这个上限是有意的——文件列表已经占了索引正文的 87%，而档案馆里动辄几千个文件的条目不少，调高会让存储涨得很快。

**很多网络访问不了 archive.org**，`probe` 会报连接超时。加代理：

```
py -3.11 btimport.py ia --limit 20000 --proxy http://127.0.0.1:7890
```

端口看你的代理客户端（Clash 常见 7890，v2rayN 常见 10809）。不指定的话 Windows 上会自动读系统代理设置，`probe` 会告诉你检测到了什么。

### 本地已有的种子文件

```
py -3.11 btimport.py folder D:\torrents
```

递归扫描 `.torrent`，名字、大小、完整文件列表全都有。**这条路不需要任何外部网络**。如果某个文件只算出 infohash、名字解析不出来，会明确报出来。

网页上走任务面板更省事，那里有「浏览…」按钮可以直接点选文件夹。

**手上没有 .torrent 可以先造一批：**

```
py -3.11 make_test_torrents.py --out test-torrents
py -3.11 btimport.py folder test-torrents
```

造出来的是结构完整、任何 BT 客户端都能解析的真 `.torrent`——bencode 编码正确、`info` 字典齐全、infohash 是照 `info` 原始字节算的 SHA-1。但它们描述的文件并不存在，piece 哈希是随机字节，拿去下载什么也下不到。这正是测索引该用的东西：要验的是解析、分词、入库、搜索，不是网络。

内容取的是 BT 上本来就合法分发的那类：Linux 发行版镜像、Blender 基金会的 CC-BY 开源动画、维基媒体转储、公开科研数据集、公版书。

最后还有十几条**分词边界用例**，每条对着一个具体的坑：中文数字粘连（`第4季`）、两字词、单字、中英无分隔混排、繁体、日文假名、韩文谚文、HTML 转义字符、FTS 查询语法关键字、LIKE 通配符、超长名字、四字节 emoji，外加一个 500 文件的种子专门验 `MAX_FILELIST` 截断。改分词相关的代码之后，拿这批重跑一遍最省事。

## 填库方式二：DHT 爬虫

```
crawler.bat
py -3.11 dhtmeta.py --sniff --db bt.db --port 6881 --with-lookup --lookup-workers 30 --workers 40 --try-peers 12
```

窗口里会一行行冒出抓到的种子名，每 15 秒打一次统计。关窗口就停。

### 统计行怎么看

```
[ 105s] 入库 2 (1.1/分)  announce 0  get_peers 340  查到持有者 237  失败 292  队列 0/0  节点池 1832  已屏蔽 7
```

- **announce** — 别人主动宣告「我有某个种子」。这是最值钱的线索，直接带着持有者地址。**需要入站可达**
- **get_peers** — 别人在找某个种子。量比 announce 大一两个数量级，但要自己去 DHT 查持有者（`--with-lookup` 干的事）
- **节点池** — 盯着这个数。如果随时间往 0 掉，是路由器 NAT 表被打爆了，继续调低 `--rate`
- **已屏蔽** — 反复不给元数据的污染 IP，自动跳过

### 网络条件决定上限

**放行防火墙 UDP 入站**：右键 `install-firewall.bat` → 以管理员身份运行。

家用路由器后面还要做 **UDP 6881 端口转发**。但如果你的宽带是**运营商级 NAT**（路由器 WAN 口 IP 落在 `100.64.x.x` ~ `100.127.x.x`），端口转发也没用，外面根本打不进来，`announce` 会长期是 0。

这种情况下只能靠 `--with-lookup` 这条主动查询的路——它只需要出网，NAT 后面照常能用，只是产出慢得多（一小时几条到几十条）。想真正把量做起来，一台有公网 IP 的 VPS 是数量级的差别。

### 关键参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `--rate` | 30 | 每秒发出的 find_node 数。家用路由器 NAT 表通常只有几千条、超时一分钟左右，150/秒会把它撑爆，表现为跑十几分钟后收发双双掉到接近零 |
| `--with-lookup` | 关 | 把 get_peers 线索也用上。覆盖率高一个数量级，流量和 CPU 吃得多 |
| `--try-peers` | 10 | 每个种子最多试几个 peer。DHT 里污染节点很多，多试几个才碰得到真的 |
| `--timeout` | 8 | 单次抓取超时。真连得上的 peer 一两秒就完事，调大只是在死 peer 上多等 |
| `--debug-fail N` | 关 | 逐条打印前 N 次抓取失败的原因和对方地址 |

## 定期维护

双击 `install-task.bat` 注册两个计划任务：

| 任务 | 时间 | 做什么 |
|---|---|---|
| BTIndex-Daily | 每天 04:00 | 体检、修索引一致性、实测 300 个种子的做种情况 |
| BTIndex-Weekly | 周日 05:00 | 以上 + 删掉确认死掉的 + 回收磁盘（删前自动备份） |

日志在 `logs\maint.log`，超过 5 MB 自动轮转保留 5 份。手动跑：

```
maint.bat
maint-weekly.bat --dry-run        试算，只显示会删什么
```

**每日任务完全非破坏性**，只读和写回实测结果。**每周任务会删数据**，条件是「实测没人在传」**并且**「30 天没再出现」，两个都满足才动手，删前备份到 `backup\bt-weekly.db`。

不想自动删就只留每日任务：`schtasks /delete /tn "BTIndex-Weekly" /f`

### 关于「死种」的诚实说明

索引里的 `last_seen` 反映的是**你的节点最后一次听到它的时间**，不是它在全网的最后活跃时间。你的嗅探实例只覆盖 DHT 键空间的一小片，种子活得好好的但没往你这片 announce，看起来就跟死了一样。

`btpeers.py` 的实测把推测变成了事实，但**单次结果仍不够**——查到 0 个只说明此刻 DHT 里没人宣告，私有种子、纯 tracker 的、靠 PEX 互相发现的都看不到。让每周任务跑几周，多次实测都是 0 的才比较可信。

磁盘不紧张的话，其实根本不用急着删。

### 在网页上删除

平时列表是干净的，只在页头统计行的右端留一个「编辑列表」。点它进入**编辑状态**，每行左边才出现勾选框，删除按钮也一并出现。再点一次（这时标签变成「退出编辑」）或者按 <kbd>Esc</kbd> 退出，退出时会自动清空已选。

删除是低频且不可逆的操作，不该常驻在每一行上——所以做成显式进入。

用户版 `web-user.bat` 带 `--no-delete`，这个按钮不渲染，勾选框和 `/api/delete` 也一起关掉。

进入编辑状态后：

- **勾选若干条 → 「删除选中 N 条」**
- **「删除当前筛选的全部 N 条」** —— 按当前的关键词 / 来源 / 体积条件整批删。几万条逐个勾不现实，所以「全选删全部」走的是这条：先把搜索框留空、各个筛选都选「不限」，按钮就会变成「删除当前筛选的全部 N 条」

两种都有确认弹窗，整批删除会问两次。删完自动刷新。

**安全上做了三件事**，因为这是个能删数据的接口：

- 只接受 POST，GET 访问删除接口直接 404
- 每次启动生成一个随机令牌嵌在页面里，请求必须带上
- 校验 `Origin`，别的网页想偷偷调你本机这个接口会被拒

读取路径**始终**是只读连接——不管加不加 `--no-delete`——只有真的执行删除时才临时开一条可写连接。加上 `--no-delete` 之后那条可写连接永远不开，「编辑列表」按钮、勾选框和接口也一起关掉：

```
py -3.11 btweb.py --db bt.db --no-delete
```

**如果你把 `--host` 改成了 `0.0.0.0`，务必加 `--no-delete`**，否则局域网里任何人都能清空你的库。

### 预览图

**种子元数据里没有图片。** BitTorrent 的 `info` 字典只有名字、分片大小、分片哈希和文件列表——`cover.jpg` 这类只是文件名，图片内容要真的下载才有。

但部分索引站会另外给封面地址（Torznab 规范里的 `coverurl`），互联网档案馆则有稳定的缩略图地址。导入时会把这个地址存下来，**只存地址，不取图**。

详情页上有封面的条目会多一个「显示预览图」按钮，**默认不显示，点了才去取**。这么做不只是为了清爽：图片托管在索引站那边，一取就等于告诉对方你的 IP。不点就不会有任何对外请求。

覆盖率看站点。多数中文站和动漫站不提供 `coverurl`，那些条目就不会有这个按钮。

**图片存在哪儿：哪儿都不存。** 索引里只有一串地址（实测每条约 75 字节），图片由浏览器直接向对方站点取，字节从不经过这个工具，工具目录里也不会出现任何图片或缓存文件。

所以「什么时候删」分两头：

- **地址**跟着条目走。删条目、按条件清空、`reset`、删库文件，地址一起没，不会残留
- **图片**由你的浏览器按对方服务器给的缓存策略存在浏览器缓存里，和这个工具无关。要清就在浏览器里清除浏览数据

想彻底不留痕迹，就别点那个按钮——不点就不会有任何对外请求。

### 清空索引

**先把爬虫和网页窗口关掉**——Windows 会锁住正在使用的文件。

**全清，最干净的做法是直接删文件：**

```
del bt.db bt.db-wal bt.db-shm
```

下次跑任何工具都会自动重建表结构，不用额外操作。

**只清某一批（保留其他来源）：**

```
py -3.11 btprune.py --db bt.db reset --source torznab        预演，看会删多少
py -3.11 btprune.py --db bt.db reset --source torznab --yes  真删
```

来源名就是导入时标的：`dht`（爬虫）、`torznab`、`ia`、`academic`、`folder`。不加 `--source` 是全清，`--backup 路径` 可以先备份。

不加 `--yes` 只是预演，还会列出各来源各多少条，看清楚再动手。

**千万别自己写 `DELETE FROM torrents`。** FTS 表没有触发器，只删主表会留下孤儿行；全表清空后 rowid 从 1 重新开始，下一个新种子插进来就撞上残留条目：

```
只删主表后 -> torrents 0 条，FTS 残留 20 条
再插入: IntegrityError -> constraint failed
```

爬虫会当场挂掉。`reset` 两张表一起清，所以是安全的。真的手滑删过，跑 `btprune.py verify --fix` 能修好。

### 手动维护

```
py -3.11 btprune.py --db bt.db analyze          体检，只读不改
py -3.11 btprune.py --db bt.db verify --fix     修 FTS 一致性
py -3.11 btprune.py --db bt.db prune --older-than 180d --max-hits 1     预演
py -3.11 btprune.py --db bt.db reset --source X  清空某一批
py -3.11 btprune.py --db bt.db vacuum           回收磁盘

py -3.11 btpeers.py check <磁力链> --verify      查单个种子现在有多少人
py -3.11 btpeers.py --db bt.db scan --limit 500  批量实测并写回索引
py -3.11 btpeers.py --db bt.db report            看分布
```

`prune` 不加 `--yes` 只是预演，会随机抽 8 条给你过目。`vacuum` 需要独占访问，跑之前把爬虫和网页都关掉。

## 从旧版升级

新建的库直接就是新结构，不用管这一节。**已经有库的才要看。**

先说不用你操心的那部分：`peers` / `checked_at`（做种数）和 `kind` / `res` / `parsed`（分类和清晰度）这几列都是**自动补的**。跑一次爬虫、导入或维护——任何要写库的东西——列和索引就都补上了，数据一条不动。网页是只读打开的，补不了列，所以纯看网页的话那两块功能会一直收着不出现。

**这一版改了名字解析规则**（带 REPACK、RELOADED、PLAZA 这类词的影视发布原先被判成游戏），所以老库要再回填一次才对得上，任务面板点「解析名字」或者 `btparse.py backfill`。不回填的话那批条目会一直待在「游戏」这一档里，用分类筛「电影」筛不到它们。

补列和**回填**是两回事，别混起来：补列是把空列加上，一瞬间的事；回填是把已有条目的名字重新解析一遍、把值填进去。分类和清晰度需要回填一次（任务面板点「解析名字」，或 `btparse.py backfill`，见上面那节），做种数不需要回填——它得去 DHT 实测，那是另一件事。

下面这节说的又是另一回事，是 FTS 表结构的迁移。**这一步不是自动的**，因为它要把全文索引整个重建一遍。

```
py -3.11 btmigrate.py --db bt.db          先估算，不动手
py -3.11 btmigrate.py --db bt.db --go     真的迁
```

不加 `--go` 只会把分表占用摊开给你看，告诉你能省多少。Windows 上双击 `migrate-fts.bat` 是同一套流程：先估算给你看，再问一句要不要真迁。

迁移做的事是另建一张新 FTS 表、把全库重新喂一遍、然后换掉旧表。实测 **77,000 条/秒**（20 万条 2.6 秒），一亿条大约 22 分钟。

**它现在管两件事**，跑一次一起办完，不用迁两次：

| 要迁的 | 老结构的毛病 |
|---|---|
| 去掉正文副本 | FTS 表里存着一份从来没人读的正文，占整个库的 47% |
| 名字和文件列表分两列 | 混在一列时排序分不出「名字里就叫这个」和「文件列表里提了一嘴」，见上面那节 |

不加 `--go` 时会先告诉你这个库差哪几项——可能只差一项，也可能两项都差。已经是新结构的库会直接说不用迁。

**两件事都不是必须的。** 老结构照样能搜能写能删，新代码认得出表结构，写入时会按老结构写。不迁的代价只是多占磁盘、排序差一点。`check.bat` 和 `btprune.py analyze` 都会提醒你库是哪种结构。

分两列之后索引本身会**大约 3%**（20 万条实测：单列 75.1 MB，两列 77.4 MB）——倒排索引里同一个词在两列里各有一份位置信息。这点代价换排序对不对，我认为值。

几件要知道的：

- **跑之前把爬虫和网页停掉**，迁移要独占写。
- **可以随时 Ctrl-C。** 已经迁好的部分留着，再跑一遍从断点接着来。旧表在最后一刻之前一直原封不动，迁移期间搜索照常可用。
- 换表前会数一遍，新索引和主表对不上就**拒绝换**并退出——旧表还在，搜索不受影响，重跑一次即可。
- 迁完腾出来的是空闲页，**文件不会自己缩**。爬虫接着写就会复用这些页，库还在长的话不用管。想立刻还给磁盘就跑 `btprune.py vacuum`，注意那一步要额外一份等同最终大小的临时空间。
- 需要 SQLite **3.43 以上**（`contentless_delete` 是那版引进的）。这不是迁移独有的要求——新建的库本来就是这个结构，版本不够整个工具都跑不起来，`check.bat` 那一关就过不去。

**库里本来就没东西的话**，最省事的办法是把 `bt.db`（连同 `bt.db-wal`、`bt.db-shm`）删掉，让新代码重建——`CREATE VIRTUAL TABLE IF NOT EXISTS` 见到已有的表就不管了，不删的话还是老结构。

怎么确认迁成功了：

```
py -3.11 -c "import sqlite3;print([r[0] for r in sqlite3.connect('bt.db').execute(\"SELECT name FROM sqlite_master WHERE type='table'\")])"
```

**没有 `torrents_fts_content`** 就说明是无正文的；`torrents_fts_docsize` 里多出一列 `origin`，那是 `contentless_delete=1` 的印记。分列迁好没有单独看一眼：

```
py -3.11 -c "import sqlite3;print([r[1] for r in sqlite3.connect('bt.db').execute('PRAGMA table_info(torrents_fts)')])"
```

出 `['name', 'files']` 就是新结构，出 `['body']` 是老的。索引现在该有十个：`idx_last_seen`、`idx_size`、`idx_hits`、`idx_source`、`idx_peers`、`idx_checked`、`idx_kind_seen`、`idx_res_seen`、`idx_parsed`、`sqlite_autoindex_torrents_1`。后面五个都是跟着功能加的，老库开一次就补齐。

`idx_kind_seen` 和 `idx_res_seen` 是**复合索引**（`(kind, last_seen)` 和 `(res, last_seen)`），不是单列的。这个形状是实测逼出来的，理由写在下面「改代码前要知道的坑」里。

`idx_source` 是后加的，老库里可能没有。但不用专门去建：`btindex.Index()` 每次以写模式打开库都会把 schema 重跑一遍，里面那句是 `CREATE INDEX IF NOT EXISTS`，所以跑一次爬虫、导入或维护它就自己回来了。只有「从头到尾只开网页」的库才需要手动补——网页是只读打开的，建不了索引——那种情况双击 `add-index.bat`。

## 数据库会长多大

实测数据（10 万条取平均，每条含名字 + 文件名，都进全文索引）：

| 每条存什么 | 每条占用 | 10 万条 | 100 万条 | 1000 万条 |
|---|---|---|---|---|
| 只有名字 | 235 字节 | 22 MB | 0.22 GB | 2.2 GB |
| 名字 + 5 个文件名 | 401 字节 | 38 MB | 0.37 GB | 3.7 GB |
| 名字 + 40 个文件名（当前默认） | 1667 字节 | 159 MB | 1.55 GB | 15.5 GB |

大头是**全文索引**，不是原始数据——中文要展开成二元组才能搜。

FTS 表建成**无正文模式**（`content=''`），只留倒排索引，不再把喂进去的 body 原样存一份。那份副本从来没人读：全文所有 FTS 访问不是 `MATCH`、`rowid` 就是 `bm25()`，要显示的字段一律从主表取，而 body 本身完全可以从 `name` 和 `filelist` 重算。600 万条的老库拆开看，`torrents_fts_content` 一张表就占 2.30 GB，而真正的倒排索引只有 0.51 GB——整个库 47% 是白占的。去掉之后上面这张表比旧版小三到五成。

嫌占地方就改 `btindex.py` 里的 `MAX_FILELIST`（默认 40）。调到 5 能省七成空间，代价是合集类种子的内部文件搜不到——而那恰恰是找冷门资源时最管用的。100 万条也就 1.5 GB，一般没必要省。

### 搜索速度

小库上随便怎么搜都是毫秒级。库大起来之后有一处要知道：

| 库规模 | 普通词 | 高频词（`1080p` 这种几乎人人都有的） |
|---|---|---|
| 100 万条 | 0.03–0.05 s | 0.09 s |
| 600 万条 | 0.37–0.55 s | 0.79 s |

**高频词是唯一不好办的。** 相关度排序要给每个命中项算 bm25 分，`1080p` 在 600 万条的库里命中 45 万条，那就得算 45 万次。这个代价跟命中数走，不跟库大小走——搜冷门词多大的库都快。FTS5 没有提前终止 bm25 排序的机制。

**英文前缀匹配会让这堵墙来得更早。** 前缀查询本身不贵——词典是按词排好序存的，前缀就是一次 b-tree 定位加一段顺序读，跟单字那个 `LIKE` 逐行扫全表完全不是一回事。贵在它把命中量放大了：`108*` 会把 1080p、1080i、1080x 全卷进来，然后 bm25 一条条算。`PREFIX_MIN`（3）挡掉了最坏的一两字母前缀，8 秒墙钟闸兜住剩下的，命令行有 `--exact`。真到一亿条上这还不够，下一步是给 FTS 表加 `prefix='2 3'` 建真正的前缀索引——短前缀会快很多，代价是索引变大、而且要像 `btmigrate.py` 那样重建一遍。**先别动，等实测证明不够快再说。**

眼下的办法是止损不是根治：网页上每条查询挂了 8 秒墙钟闸（`QUERY_DEADLINE`），超时明说「这个搜法太慢，换个更具体的词」，而不是把工作线程按住几分钟、用户那头一直转圈然后刷新再来一条把线程堆起来。

### 库大了之后，慢的往往不是搜索

这几处都是**每打开一个页面都要付**的代价，600 万条上实测：

| 动作 | 老写法 | 现在 |
|---|---|---|
| 顶栏「库里 N 条 / 内容总量」 | 3.86 s | 0.00 s |
| 来源下拉（`GROUP BY source`） | 3.14 s | 0.00 s |
| 搜单个汉字（退回 LIKE） | 15.69 s | 0.28 s |

三件事：

**统计数字加了缓存。** 顶栏那行和来源下拉原本每次都扫全表，而且是线性涨的——一亿条就是每开一个页面等两分钟。现在超过 10 万条才启用缓存（`STATS_CACHE_FROM`），过期时先把旧值交出去、后台再刷。十万条以内不缓存，直接实算：那时候扫一遍才几十毫秒，套缓存反而会出怪事——刚导完一批，页面列着 80 条，顶栏却写「库里 0 条」。判空也不走缓存，用 `SELECT 1 FROM torrents LIMIT 1`，常数时间。启动时会在后台先算一遍垫掉首次开销。

**`get_stats` 拆成了三条查询。** 写成一条 `COUNT + SUM + MAX`，SQLite 只能 `SCAN torrents`（600 万条 2.5 秒）；拆开之后每条走各自的覆盖索引，只读索引不碰主表，合计 0.9 秒。**同样的数据，三次查询比一次快三倍。**

**单字搜索划了窗口。** 单个汉字 FTS 够不着（二元组和整串都配不上），只能退回 `LIKE` 逐行比对，代价跟着库线性涨。现在只扫最近入库的 50 万条（`LIKE_WINDOW`），结果页会明说这件事。命令行加 `--deep` 可以解除。

## 关于用途与边界

这套工具做的事是：**索引 BitTorrent DHT 网络上公开广播的元数据**，以及从你自己配置的索引站聚合条目。

它不托管、不传输、不分发任何内容——数据库里存的只有名字、体积、文件列表和 infohash。真正的下载由你自己的 BT 客户端完成，和本工具无关。

DHT 上流通什么内容是使用者无法控制的。几个边界值得说清楚：

- **自己本地建索引使用**，和**把索引做成对外开放的公共服务**，在法律上是完全不同的两件事。后者在国内外都有运营者被追责的先例
- 工具默认只监听 `127.0.0.1`，改 `--host` 对外开放前请自行评估
- `btimport.py` 能接哪些索引站，完全由使用者在 Jackett 里自行配置，本工具不内置任何站点列表
- 内置的两个导入源（互联网档案馆、Academic Torrents）都是公开的公益资料库

代码按原样提供，使用者自行承担使用后果。

## 排错

**双击 .bat 闪一下就没了**
`_env.bat` 没找到 Python。开命令行 `cd` 到工具目录再执行 `check.bat`，能看到具体报错。

**提示目录不可写**
别放 `C:\Program Files` 或系统盘根目录，普通用户没写权限。放 `D:\btsearch` 这种自己的目录。

**爬虫 announce 一直是 0**
入站不通。先确认 `install-firewall.bat` 以管理员身份跑过（`netsh advfirewall firewall show rule name="BT DHT Crawler"` 能查），再看路由器有没有端口转发。如果是运营商级 NAT 就没办法，只能靠 `--with-lookup`。

**爬虫跑十几分钟后收发都掉到接近零**
路由器 NAT 表被打爆。调低 `--rate`，盯着统计行里的「节点池」，它不掉就是稳的。

**Jackett：`code=100 Invalid API Key`**
Key 复制错了，或者竖线两边带了空格。

**Jackett：`Connection refused`**
Jackett 没在运行，或端口不是 9117。

**Jackett：caps 通了但 search 超时**
这两步性质完全不同：`caps` 由 Jackett 本地回答不出网，所以永远很快；`search` 是 Jackett 真的去各个索引站抓。用 `all` 时要等所有站返回，一个连不上的就拖垮整批。跑 `--each` 逐个测，然后只用能用的那几个站。

**Jackett：某些站 HTTP 400 / IndexerException**
Jackett 连不上那些站。去 Jackett 右上角 **Logs** 看具体是 DNS 失败、连接超时还是 Cloudflare 拦截。前两者在 Jackett 设置里配代理（齿轮 → Proxy Type / Proxy URL / Proxy Port），后者需要另外搭 FlareSolverr，地址填在同一页。

**注意：本工具的 `--proxy` 对 Jackett 这段没用**——我们连的是 `127.0.0.1`，本来就通。要代理的是 Jackett 出去抓站点那一段。

**Jackett：能搜到但都没有磁力链**
那些站只给 `.torrent` 下载地址，或者给的是 Jackett 的 `/dl/` 代理地址。加 `--fetch-torrents`，工具会把种子取下来自己算 infohash。这条路拿到的信息反而更全——种子文件里有真实名字、准确大小和完整文件列表。

**archive.org 连接超时 / Academic Torrents 报 `SSL: UNEXPECTED_EOF_WHILE_READING`**
两种症状不同但原因一类：站点在你的网络里不可达。前者是握手都没开始就超时，后者是 TLS 刚建立就被重置——**不是证书问题**，加代理就行：

```
py -3.11 btimport.py academic --proxy http://127.0.0.1:7890
```

网页任务面板里也有「代理」那一栏，填上即可。

连续失败 3 次会自动停下，不会把剩下的关键词一个个试完让你干等。

**一个站通、另一个站不通，多半是代理在分流。** Clash、v2rayN 这类客户端默认按规则走：收录过的域名走代理，没收录的走直连。所以 `archive.org` 能通而 `academictorrents.com` 不通，是很常见的情况——不是代理没开，是这个域名没被规则匹配到。

两个办法：把客户端切到**全局模式**，或者给 `academictorrents.com` 单独加一条走代理的规则。

每次导入开头都会打出代理状态，别靠猜：

```
代理：http://127.0.0.1:7890
代理：未指定 --proxy，将使用系统设置 http=...
代理：无，直连
```

各个源互相独立，这两个不通完全不影响用 Jackett 或本地种子文件夹导入——**后两条路根本不需要访问境外站点**。

**网页打不开 / 提示打不开数据库**
`bt.db` 还不存在。先导入或跑一会儿爬虫。

**计划任务显示退出码 2**
表示「上一次维护还在跑，本次跳过」，是正常的保护机制。上次异常中断的话，锁文件超过 12 小时会自动接管。

**vacuum 失败**
需要独占访问数据库。把爬虫和网页都关掉再跑。每周任务撞上爬虫时这一步会失败但不影响其他步骤，日志里会标出来。

**控制台里中文是乱码**
Windows 老版本控制台的问题。工具已把输出强制设成 UTF-8，终端本身不支持的话换 Windows Terminal。日志文件本身是 UTF-8。

## 改代码前要知道的坑

这几处踩过，记下来省得重犯。

**FTS 表没有触发器。** `torrents_fts` 只在 `btindex.upsert` 里手动同步。如果写了一句朴素的 `DELETE FROM torrents`，FTS 里会留下孤儿行；SQLite 回收 rowid 之后，下一个新种子插入时会撞上残留条目，**直接 IntegrityError 让爬虫崩掉**。任何删除都必须先删 FTS 再删主表。定期跑 `btprune.py verify --fix` 能查出并修好。

**FTS 是无正文表，但用起来和普通表一样。** `content=''` 加 `contentless_delete=1`，所以 `DELETE FROM torrents_fts WHERE rowid=?` 照常能用，`bm25()` 也照常（docsize 还存着，只是正文不存）。唯一的区别是 `SELECT body FROM torrents_fts` 返回 `NULL`——但全文没有一处需要读它。改代码时别加读 body 的逻辑，要原文从主表的 `name` 和 `filelist` 取，或者用 `expand_text` 重算。另外无正文表删行会留墓碑，久了索引虚胖，`btprune.py vacuum` 里的 `'optimize'` 就是收这个的。

**`SCHEMA` 跑在补列之前，所以里面不能出现引用新列的语句。** `peers` / `checked_at` 是后加的两列：新库由 `SCHEMA` 的 `CREATE TABLE` 带出来，老库靠 `ensure_columns()` 的 `ALTER TABLE` 补上。但 `Index.__init__` 是先 `executescript(SCHEMA)` 再补列的，所以 `SCHEMA` 里写一句 `CREATE INDEX ... ON torrents(peers)` 就会在老库上直接 `no such column: peers`，**每一次打开库都炸，而且只炸老库**——新库一点事没有，自己测十遍都发现不了。这两个索引现在建在 `ensure_columns()` 末尾，无条件执行、靠 `IF NOT EXISTS` 幂等。**以后再加列，索引和任何引用它的语句都要放到补列之后。** `kind` / `res` / `parsed` 三列是照这条规矩加的，它们的定义和索引都在 `btparse.ensure_parse_columns()` 里，`btindex.ensure_columns()` 调过来——**同一件事只写一份**，上一轮 `peers` 差点漂成「一边建了索引一边没建」就是因为两处各写了一遍。

**`-1` 和 `0` 不是一回事。** `peers` 的 `-1` 是「从来没测过」，`0` 是「测过、当时一个人都没有」。合并成一个值会让界面把「不知道」说成「没人」，而这恰恰是用户最该分清的两件事。`WHERE peers > 0` 不能写成 `>= 0`，API 返回 `-1` 时也不要在服务端替调用方折成 0。

**前缀的星号写在引号外面。** `"ubun"*` 是前缀查询，`"ubun*"` 是在找一个真的带星号的词，一条都搜不到。引号本身不能省——`build_match` 给每个词加引号是为了挡注入，用户输入里的 `AND`、`NOT`、`(` 才不会把 MATCH 表达式带跑偏（`make_test_torrents.py` 里有专门一条用例盯这个）。

**页头是一整套状态，不是装饰。** 搜索页、详情页、任务面板共用一个 `page()`，但早先只有搜索页那条路把参数喂全了，另外两条只传了标题、正文和统计。结果页头上的筛选控件全是空壳：来源下拉只剩一个空选项，分类和清晰度干脆不渲染（它们要 `show_parse` 才出现），搜索框里的词也没了。**控件在那儿、看着能用、其实全是默认值**，比干脆不显示更误导——而且不报错，得有人眼睛扫到才发现。

同一个错犯了两次（详情页一次、任务面板一次），所以第二次没打补丁：页头那一整套状态现在只有一个出处，`Handler.header_state()`，三条路都调它。**以后再给页头加控件，改这一个函数就够，不用记得去喂三个地方。**

状态还要跟着链接走：结果行的详情链接、页头上的「任务」链接，都带着当前这一屏的筛选，所以来回切不丢。回来的那个「本地搜索」链接不用带——它指向 `/`，而 `/` 会用 `LAST_VIEW` 把人送回上一次真正看过的那一屏，连页码都在。

**页头按东西的性质分行，不要交给浏览器按剩余宽度断。** 筛选控件和动作原来挤在同一排，一满就换行，换出来的那行只有两个动作孤零零挂着，看着像排版塌了。问题不是换行本身，是那排混了两类东西——五个下拉是「选一个值」，后面两个一个是导航一个是模式开关——浏览器只按剩余宽度决定断点，断在哪儿必然随机。现在按性质分：控件行只放筛选，动作挪到统计行右端（那行右边本来就空着，不多占高度，反而少一行）；做种那个勾选框是开关不是下拉，用 `margin-left:auto` 顶到行尾，和下面的动作对齐成一列，宽度不够时它单独落到下一行，落点仍在右端。站名那一行整个去掉了，导航挪到搜索按钮右边做成同样大小样式的按钮，站名只留给标签页标题和屏幕阅读器。**页头从 238px 降到 176px。**

那个按钮只有一个功能：去任务面板。不做成随页面换名字的切换键——**回列表不需要它，旁边那个「搜索」就是**，在任务面板上按一下（搜索框留空或者填个词）就回到列表了。和「浏览全部」是同一条道理：一个只是别处快捷方式的控件，不如不要。

**递归解析器喂的是陌生人发来的东西，必须有深度上限。** `bdecode` 原先没有，`l` 重复五千次再补五千个 `e`——一个十 KB 的包就能顶穿递归栈抛 `RecursionError`。要紧的不是会抛异常，而是抛的**类型**：各处收包循环接的是 `except Exception`，不受影响；但 `dhtmeta` 里逐个试 peer 的 `try_peers` 接的是 `(MetaError, OSError, ValueError)`，`RecursionError` 不在其中，会直接冲出那个循环——于是**一个恶意 peer 就能让剩下的 peer 一个都不再试**，那个种子就此放弃。DHT 上确实有人专门投毒（所以这份代码里才有 `polluters` 那一套）。修在解析器自己身上、抛 `ValueError`，七个调用点一次全覆盖；`try_peers` 那处顺带放宽成 `except Exception`，因为它的语义本来就是「这个不行换下一个」，漏掉任何一种异常类型代价都是放弃一整批。

**自检工具得认 `--help`，否则它会递归跑自己。** `scan_bat_flags` 的做法是对每个 `.bat` 里提到的脚本跑一次 `--help` 收集参数，而 `btcheck.py` 自己就写在 `check.bat` 里——它原先忽略一切参数直接开跑，于是自检会起一个子进程递归地跑自己，跑满 30 秒被 timeout 杀掉才算完。整个自检 36 秒里 30 秒耗在这一件事上，全程不显示进展，看着就像卡死。修掉之后加上 `flags()` 的结果缓存（14 个 `.bat` 里同一个脚本会被提到好几次），36 秒变 6 秒。

**关掉的功能，入口要跟着消失。** 这个按钮原来是无条件渲染的，而 `/api/task` 那边早就对 `--no-tasks` 返回 403 了——也就是说加了 `--no-tasks` 之后，页头最显眼的位置还杵着一个按下去只会报错的按钮。现在它跟 `TASKS[0]` 一起开关。同一条道理还管着页面正文里那些「去任务面板点一下」的提示（空库引导页、落地页、详情页的「还没测过」和「补全文件列表」、零结果时的两句）：解释「为什么是零条」的前半句两版都留，「去按哪个按钮」的后半句只对管理版说，用户版没有那个按钮，说了只是把人指到一堵墙上。

**去掉它之后搜索按钮自己就靠右，不用加一行样式。** 搜索框是 `flex:1 1 280px`，这一行剩下的宽度全被它吃掉，所以排在最后的元素必然顶在行尾——原来最后一个是「任务」，现在是「搜索」。想靠 `margin-left:auto` 来「实现」这个右对齐是白写的：free space 已经被搜索框吃光了，auto 边距分不到任何东西。

配套的一个坑：全局有一条 `a:hover{text-decoration:underline}`，优先级是 (0,1,1)，压得过 `.go` 里那句 `text-decoration:none`（0,1,0）。所以**按钮如果是个链接，`:hover` 那条规则里得把 `text-decoration:none` 再写一遍**，否则鼠标一放上去按钮里就冒出条下划线。`.go:hover` 是 (0,2,0)，压得住。

**一个按钮如果只是另一条路的快捷方式，那它多半不该存在。** 原来页头上有个「浏览全部」，指向写死的 `/?q=`。但搜索框留空直接按搜索就是同一件事——而且更好：它保留当前的筛选，而那个链接会把筛选一起清掉。两条路看着一样、行为不一样，是比少一个按钮更糟的事。删掉之后落地页上留了一句话说明「留空就是浏览全部」，这比一个按钮更省地方也更说得清。

顺带一条：**`select` 的宽度由最长的那个选项决定**，所以空值选项的写法直接影响整排控件的宽度。「全部分类」「清晰度不限」「全部来源」一律改成「不限」——每个下拉前面都有自己的标签，把类别名再写进选项里是重复的，省下的宽度正好够那个勾选框留在同一行。体积那档同理，「1 GB 以上」改成「≥ 1 GB」。

**任何筛选条件都要同时穿过搜索、计数、删除三条路。** 搜索、「共 N 条匹配」、「删除当前筛选的全部 N 条」共用同一套条件，这是故意的：三者必须看到同一个结果集，否则会出现页面列了 50 条、点删除只删掉 12 条这种事。好处是不用额外同步，代价是**放宽匹配规则会同步放宽删除范围**——加前缀之后搜 `2160` 从 0 条变成 7 条，那个删除按钮删的也就是这 7 条。**新加一个筛选项时，漏掉 `delete_by_filter` 的后果是页面列了 12 条、点删除删掉 400 条，而且不可逆。** 加完一定要实测一遍三者的数字对不对得上。

条件从两个涨到四个（体积、来源、`alive`、`kind`、`res`）之后，靠人记着同步三处已经不现实了，所以现在只有**一个出处**：`btweb.filter_clauses()`。三条路都调它，只有关键词那一段因为 SQL 形状不同才各自拼。再加筛选项就改这一个函数，别再往三处各写一遍 `WHERE`。

**筛选列的索引要带上排序列，光建一个单列索引不够。** 浏览全部默认按最近出现排，于是查询是 `WHERE kind=? ORDER BY last_seen DESC LIMIT 26`。SQLite 有两条路可选：用 `idx_kind` 定位再排序，或者顺着 `idx_last_seen` 扫下去逐行验 `kind`——它选了后者，因为那样不用排序。分类常见时看不出问题，扫二十几行就凑够一页了；**分类稀有时就是一路扫到底**：20 万条的库里筛一个只有 5 条的分类要 0.058 秒，而这个数跟着库线性涨，一亿条上就撞 8 秒闸了。改成复合索引 `(kind, last_seen)` 之后同一条查询变成一次索引定位加一段顺序读，实测 **0.058 秒变 0.00004 秒**，而且不随库长大。复合索引还顺便顶替了单列索引——`WHERE kind=?` 和 `GROUP BY kind` 都走它的覆盖扫描，所以不用再单建一个。**以后给新列加筛选，索引直接建成 `(新列, last_seen)`。**

**给 bm25 多传权重，单列的表不会报错。** 这一条决定了这次改动的代价：`bm25(torrents_fts, 10.0, 1.0)` 在只有一列的老表上照样跑——多出来的权重被忽略，剩下那个权重对所有行是同一个倍数，排序一点不变（实测确认前十名和 `bm25(torrents_fts)` 完全一致）。所以**读和排序那一侧根本不用分两套代码**，只有写入要认表结构。判断结构用 `PRAGMA table_info(torrents_fts)`，虚表也认这个。

**索引正文的拼法只能有一个出处。** 名字和文件列表怎么拼进 FTS，原来有三份各写一遍的代码：`btindex.upsert`、`btprune` 的修复、`btmigrate` 的重建。差一个空格，修复补回去的条目搜出来的结果就和别人不一样，而且不报错。现在统一走 `btindex.fts_write()`，它同时知道该写一列还是两列。`btmigrate` 那份没法复用（它写的是另一张表名），但注释里钉死了必须一致。

**一个字段只能有一个出处，包括 API 里。** `kind` / `res` 存在库里（筛选用的就是它们），年份、季集、片源、编码是每次现算的。API 早先把整个解析结果原样塞进 `parsed` 字段，于是 `kind` 在响应里出现了两次——而规则改过还没回填时，这两个值可能不一样。现在 `parsed` 里只放不进库的那几样。同理，界面上行内标签的分类和清晰度也必须取库里的值，不能现算：**显示的和筛选的必须是同一个值**，否则会出现「标着电影、按电影筛却筛不到」。

**`ORDER BY` 会悄悄废掉你的扫描范围。** 单字搜索加了 `rowid > MAX-50万` 的窗口，但第一版根本没生效：`ORDER BY t.hits DESC` 诱使 SQLite 走 `idx_hits` 从头扫整个索引、逐行回表验 rowid，查询计划里是 `SCAN t USING INDEX idx_hits`，窗口退化成一个过滤器，该扫多少还是扫多少。在排序表达式前加一个**一元加号**（`ORDER BY +hits DESC`）让它不再对应任何索引列，计划才改成 `SEARCH t USING INTEGER PRIMARY KEY (rowid>?)`。实测 1.21 秒变 0.26 秒。**加了范围条件之后一定要 `EXPLAIN QUERY PLAN` 确认它真的在用**，不然自我感觉良好而已。

**聚合写在一条 SQL 里可能比拆开还慢。** `SELECT COUNT(*), SUM(size), MAX(last_seen)` 合在一条，SQLite 只能全表扫，因为没有哪个索引同时覆盖 size 和 last_seen；拆成三条则各走各的覆盖索引，只读索引不碰主表。600 万条上 2.5 秒变 0.9 秒。

**缓存要挑规模用。** 统计数字加缓存是为了救大库，但小库上它只会添乱：过期那一下先交旧值、后台再刷，于是刚导完数据，页面列着 80 条、顶栏写「库里 0 条」。现在超过 `STATS_CACHE_FROM`（10 万）才缓存，以下实算。判空更不能走缓存——错报「索引还是空的」正好撞在第一次用的人刚导完那一刻。

**滚动条会让居中布局左右晃。** `.wrap` 是 `margin:0 auto` 居中的，一页有纵向滚动条一页没有，可用宽度就差一个滚动条，居中点跟着挪半个（Windows 上约 8px），切页时整幅界面横晃一下。`html{scrollbar-gutter:stable}` 让那条槽常驻。必须写在 `html` 上，写 `body` 上不生效。

**infohash 是内容的哈希，所以名字不会变。** 同一个 infohash 再次出现只累加 `hits`，不用更新名字。`hits` 顺带成了一个免费的热度指标。

**重建 .torrent 时 info 部分必须原样塞回。** 解码成字典再重新编码，字节序稍有出入 infohash 就变了，重建出来的种子谁都下不动。

**Windows 上不能开 SO_REUSEADDR。** 它在 Windows 上的意思是「允许别的进程抢占已占用端口」，两个嗅探实例会同时绑上同一个端口、随机分流，症状是收获莫名其妙减半且极难排查。`btcompat.bind_udp()` 按平台做了区分。

**读子进程输出时也必须显式指定 `encoding="utf-8"`。** `subprocess.run(text=True)` 在 Windows 上会用系统区域编码（中文版是 GBK）去解码，而我们的脚本都把自己的输出设成了 UTF-8——两边对不上就在读取线程里抛 `UnicodeDecodeError`，`r.stdout` 变成 `None`，外面一拼接就是 `TypeError`。这是下面那条坑的翻版，同一个原因换了个位置。

**输出重定向到文件时必须显式设 UTF-8。** 中文版 Windows 默认 GBK，程序输出到控制台时不会崩，但一重定向（计划任务就是这么干的）就在 `✓` 这类字符上抛 UnicodeEncodeError，任务当场死掉。`btcompat.setup_console()` 处理了这个。

**Torznab 的 infohash 藏在很多地方。** `<torznab:attr>`、`<link>`、`<guid>`、`<enclosure>` 都可能，还有 base32 形式的磁力链。只认一两处会把大量条目误判成「没有磁力链」。

**Jackett 的 `/dl/` 地址对磁力站是 302 跳转到 `magnet:`。** urllib 自动跟随会在 `magnet:` 上抛 unknown url type。必须禁掉自动跟随、自己读 Location。

**argparse 的选项默认只认写在子命令前面。** 人会自然地写在后面。解法是给每个子命令也加一份、`default=argparse.SUPPRESS`，这样顶层传进来的值不会被子命令的默认值冲掉。`check.bat` 里有针对这个的回归检查。

**别用 `except Exception: pass`。** 这套工具里最难查的几个问题全是被吞掉的异常：爬虫抓取失败、Jackett 列站失败、种子解析失败，症状都只是「结果为 0」，没有任何线索。统计原因、打印出来，排查时间能从几小时降到几分钟。
